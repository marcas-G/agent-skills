# E-3 梳理器：现状理解与盲区标记

目标：产出一**外部人可读**的现状梳理，作为对齐与诊断的事实底座。

## 必守不变量

- INV-3.1 每条功能描述必须锚定代码证据（文件/入口点），无锚点的条目删掉。
- INV-3.2 盲区与功能清单互斥：没读懂的区域进「盲区」，不进功能清单，不许猜。
- INV-3.3 项目存在 docs/SE 时，以 SE 的需求（P2）与架构（P4）为基线**增量核对**（找实现漂移），不重头猜。

## 步骤

1. 读目录结构 + 入口文件（main/路由/导出）+ 构建/包配置 → 划模块边界。
2. 逐模块归纳：对外功能（做什么）、内部职责（管什么）、需求线索（为谁/为何）。
3. 深度按范围定：全库=功能级；模块=行为级；文件=逻辑级。**控制成本，不逐行通读**。
4. 有 SE 基线：逐条核对 SE 条目 vs 代码现状，漂移处单独列出（这是诊断器「与理解不符」的输入）。
5. 置信不足（读不懂/信息矛盾/超成本）的区域 → 记入盲区，标注原因。

## 产出

写入 `docs/refactor/<round>/survey.md`：

```markdown
# 现状梳理：<范围>
## 功能清单（每条带锚点）
- F1 <功能描述> — 证据：<文件:符号/入口>
## 模块职责现状
- <模块>：<职责>（与名实是否相符）
## 需求线索
- <从代码推断的为谁/为何，标注推断置信度>
## SE 基线核对（如适用）
- <SE 条目> vs 现状：<一致/漂移：描述>
## 盲区（未理解，禁止猜测）
- <区域>：<原因（复杂度/矛盾/超成本）>
## 覆盖率自评
已锚定功能 N 条 / 预估总功能 M 条 ≈ <x>%；盲区 <k> 处
```

完成后让协调器执行：`log survey-done {"blindspots":[...],"coverage":"<x>%"}`
