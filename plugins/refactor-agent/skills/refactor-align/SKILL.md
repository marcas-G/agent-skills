# E-4 对齐器：意图对齐（决策①）

目标：把「代码在做什么」与「现在想要什么」对齐。**只对齐，不评价好坏**（那是诊断器的事）。

## 必守不变量

- INV-4.1 对齐文档中「最新理解」的每条必须可追溯到用户的原话或选择——**你不得发明意图**。
- INV-4.2 本文档未完成前，不得进入诊断阶段。

## 步骤

1. 读 survey.md，提取**值得发问的差异点**：代码现状与 SE 基线矛盾处、明显的半成品/绕行实现、命名暗示了但未实现的行为。只问这些，不泛泛发问（每问都有上下文）。
2. 差异点 ≤5 个为宜；超过则按影响挑前 5，其余记入「未问差异」节。
3. 每问生成：现状描述（引 survey 锚点）+ 疑问 + 选项（含默认推荐）。交协调器用 AskUserQuestion 呈现。
4. 用户全部答复后，合并成对齐文档。

## 产出

写入 `docs/refactor/<round>/alignment.md`：

```markdown
# 对齐后理解：<范围>
## 现状摘要（来自 survey，不重复展开）
## 差异裁决（决策①记录回引）
- Q1「<问题>」→ 用户选择：<选项>（含义：<...>）
## 最新理解（每条可追溯到用户输入）
- R1 <需求/功能理解> — 来源：Q1 选择
## 未问差异（本轮未覆盖，留待诊断参考）
- <...>
```

用户拒绝回答/超时 → 文档标记「意图未更新，按现状理解继续」；后续诊断的「与理解不符」类自动降权。
