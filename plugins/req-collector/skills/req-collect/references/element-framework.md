# 五要素框架与加工判据（E2 要素加工器）

> 判据是规则不是即兴：同一输入 + 相同草稿上下文 → 相同加工结果。

## 五要素定义与齐备判据

| 要素 | 是什么 | 齐备判据（全部满足才算 ●） |
|---|---|---|
| 问题 | 要解决的现实困难 | 主体、场景、障碍三件齐——能写成"谁在什么情况下难以做什么" |
| 场景 | 典型使用流 | 主路径步骤 ≥1 步，每步含"谁做什么" |
| 干系人 | 谁影响/被影响 | 角色 ≥1 个，且各带具体关切（具体到能影响验收方向即可，不要求验收标准已定） |
| 边界 | 做什么/不做什么 | In Scope ≥1 且 Out Scope ≥1 |
| 验收标准 | 怎么算做成 | 可判定条目 ≥1（"给定 X，应能 Y"式） |

**验收标准反例（禁）**："系统应支持导出"——愿望句不可判定。改写方向："给定已收集的需求文档，用户应能一键导出为 Markdown 文件到项目目录"。

## 检测判据

- **空白**：要素节为空，或内容仅含标记（[UNRESOLVED]/[CONFLICT]）→ ？（优先暴露未决）
- **矛盾 vs 细化**（关键判别）：
  - **矛盾**：新输入与草稿在**同一断言点**给出不相容取值（发 vs 不发、自动 vs 手动、数值/对象/范围不同）→ `[CONFLICT: 旧说法 | 新说法]`
  - **细化**：新信息是既有断言的具体化（对象/方向一致，仅增加细节，如"自动汇总"→"组长点一下后自动汇总"）→ 判细化，写入并**在变更记录里注明判定理由**
  - 两可时倾向 CONFLICT（宁可多问一句，不可静默择一）
- **切分**：一段输入中出现 ≥2 个互不隶属的问题主体或目标 → 拆成多个需求
- **未决**：要素无法从输入确定 → `[UNRESOLVED: 缺什么/为什么定不了]`

## 验收草拟规则

允许从用户**已提供的其他要素原文**（场景/边界）提炼草拟验收条目，但：

- 必须标"（草拟，待确认）"，并在追问中请用户确认；确认后才算齐备 ●。
- 用户以明确语句给出的验收例子/条目 = 已确认（用户原话），不标草拟。
- 禁止凭空生成用户没说过的验收条目；用户"你看着办"之类委托**不产生内容**（INV-4），标 [UNRESOLVED]。

## 归位规则

- 按要素语义匹配；一句话里含多要素信息（如"销售在手机上提单老失败，希望能在电脑上批量导入"）→ 拆开：问题→"销售移动端提单失败"，场景/边界线索分别归位。
- 归位不确定 → 放 [UNRESOLVED] 请用户指认，不硬归。
- 与需求无关的内容（寒暄、上下文铺垫）忽略，但**告知用户忽略了什么**，不静默丢弃。

## 追问库（从未齐备要素 ◐/○ 取材，生成后必须过滤已问历史）

- 问题：谁遇到这个问题？什么情况下？现在卡在哪？
- 场景：走一遍典型过程，谁第一步做什么？
- 干系人：谁会用/谁会被影响？他们各自在意什么？
- 边界：第一版必须做什么？明确不做什么？
- 验收：做成之后怎么判断它成了？给一个能判"过/不过"的例子。
